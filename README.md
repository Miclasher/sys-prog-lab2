# Лабораторна: профілювання множення матриць

Програма `matmul.c` множить дві матриці N×N (double). Має два варіанти алгоритму:

| Варіант | Порядок циклів | Особливість |
|---|---|---|
| `ijk` | i → j → k | внутрішній цикл читає **стовпець** B з кроком N×8 байт → багато cache-miss |
| `ikj` | i → k → j | внутрішній цикл читає **рядки** B і C послідовно → кеш працює, компілятор векторизує (AVX) |

Оптимізацію показуємо двома способами (завдання дозволяє обидва):
1. ключі компілятора: `-O0` → `-O3 -march=native`;
2. зміна коду: `ijk` → `ikj`.

---

## 0. Підготовка середовища

Потрібен **нативний Linux** (не WSL і бажано не віртуалка): у VM/WSL часто недоступні апаратні лічильники і RAPL (енергія).

```bash
sudo apt install build-essential git linux-tools-common linux-tools-$(uname -r) powerstat
# дозволити perf збирати дані без обмежень (до перезавантаження)
sudo sysctl kernel.perf_event_paranoid=-1
sudo sysctl kernel.kptr_restrict=0

make            # збирає matmul_O0, matmul_O3, асемблер *.s і vec_report.txt
./matmul_O0 1024 ijk
./matmul_O3 1024 ikj
```

Чому в Makefile `-g -fno-omit-frame-pointer`: на `-O3` компілятор викидає frame pointer, і `perf -g` не може розкрутити стек → FlameGraph «ламається». Ці ключі зберігають імена функцій і стек.

Якщо `ijk` на `-O0` працює занадто довго — візьміть `N=512` або `768`. Головне: використовуйте **однаковий N** у всіх вимірах.

## 1. FlameGraph (п. 1.1, 1.2)

```bash
./scripts/flamegraph.sh ./matmul_O0 1024 ijk
# відкрити results/matmul_O0_ijk.svg у браузері
```

Що робить скрипт (це треба проговорити на захисті):
1. `perf record -F 99 -g` — 99 разів на секунду перериває програму і записує поточний стек викликів;
2. `perf script` — перетворює бінарний `perf.data` у текст;
3. `stackcollapse-perf.pl` — «згортає» однакові стеки в рядки `main;matmul_ijk 412`;
4. `flamegraph.pl` — малює SVG.

**Як читати графік:**
- вісь X — **не час**, а частка семплів (ширина = скільки CPU-часу функція і її нащадки забрали); порядок зліва направо — алфавітний;
- вісь Y — глибина стеку: знизу `main`/`_start`, вище — викликані функції;
- «плато» нагорі = функція, яка сама витрачає час.

Очікуваний результат: майже вся ширина — `main → matmul_ijk`, вузька смужка `init_matrix`/`rand`, ще вужча `checksum`. Висновок: вузьке місце — потрійний цикл, оптимізувати треба саме його.

Для всієї системи (опційно): `sudo perf record -F 99 -a -g -- sleep 10`, поки програма працює в іншому терміналі.

## 2. Статистика виконання (п. 2.1–2.3)

```bash
./scripts/stats.sh ./matmul_O0 1024 ijk
```

### 2.1 `/usr/bin/time --verbose`
Ключові поля для пояснення:
- **User time** — час CPU в режимі користувача (тут майже весь); **System time** — у ядрі (malloc/page faults, мізерний);
- **Percent of CPU** ≈ 99% → програма однопотокова і CPU-bound;
- **Elapsed (wall clock)** — реальний час;
- **Maximum resident set size** ≈ 3 × N² × 8 байт (3 матриці; для N=1024 ≈ 24 МБ + накладні);
- **Minor page faults** ≈ RSS / 4 КБ — ядро виділяє сторінки при першому записі;
- **Voluntary/Involuntary context switches** — скільки разів процес віддав/забрали CPU.

### 2.2 `perf stat -d`
- **task-clock, CPUs utilized** — скільки ядер реально завантажено;
- **cycles, instructions, IPC** (insn per cycle) — у наївному варіанті IPC низький (< 1), бо процесор чекає на пам'ять;
- **branches / branch-misses** — циклів багато, але вони передбачувані → % промахів малий;
- **L1-dcache-loads / L1-dcache-load-misses**, **LLC-loads / LLC-load-misses** — головне для нашої програми: в `ijk` високий % промахів через доступ до B по стовпцю.

### 2.3 `perf record` + `perf report`
- `perf report` показує функції, відсортовані за % семплів (Self / Children);
- натисніть Enter на `matmul_ijk` → **Annotate** (або `perf annotate`) — побачите конкретні асемблерні інструкції, на які припадає найбільше семплів (зазвичай завантаження з B — там і чекає процесор).

## 3. Енерговитрати (п. 3.1, 3.2)

```bash
sudo ./scripts/energy.sh ./matmul_O0 1024 ijk
```

Інструмент — **Intel RAPL** (Running Average Power Limit, на AMD Zen теж є): лічильники в процесорі, які рахують джоулі.
- `power/energy-pkg/` — весь пакет CPU (ядра + кеш + контролер);
- `power/energy-ram/` — пам'ять (є не на всіх CPU);
- ще можна `power/energy-cores/`. Список: `perf list | grep power`.

**3.1 Система:** `perf stat -a -e power/energy-pkg/ ./prog` — енергія всього процесора за час роботи програми. Альтернативи для «творчості»: `powerstat`, `turbostat`, `s-tui` (графік потужності), розряд батареї ноутбука з `/sys/class/power_supply/BAT0/energy_now`, або **розумна розетка/ватметр** — це реально вся система включно з блоком живлення.

**3.2 Тільки програма** (RAPL не знає про процеси, тому оцінюємо):
- **метод різниці**: `E_prog ≈ E(з програмою) − E(простій за той самий час)` — скрипт робить це автоматично;
- **метод частки CPU**: `E_prog ≈ E_pkg × (CPU-час процесу / сумарний CPU-час усіх процесів)`;
- готові per-process інструменти: **PowerJoular**, **Scaphandre**, **Kepler** — можна показати як «творчий» підхід.

Робіть 5–10 повторів і беріть середнє — енергія сильно «шумить». Перед замірами закрийте браузер та інші програми.

## 4. До і після оптимізації

### 4.1 Асемблер
Після `make` є `matmul_O0.s` і `matmul_O3.s`. Зручніше показати на **godbolt.org**: вставте функції, компілятор x86-64 gcc, ключі `-O0` і окремо `-O3 -march=native`.

Що пояснити:
- **-O0**: кожна змінна (`i`, `j`, `k`, `sum`) живе в пам'яті на стеку — постійні `mov ... -20(%rbp)`, індекси `i*n+k` перераховуються на кожній ітерації через `imul`, одна скалярна операція за раз (`mulsd`, `addsd`);
- **-O3**: змінні в регістрах, множення індексів замінені інкрементом вказівника (strength reduction), розгортання циклів (loop unrolling), без зайвих звернень до стеку.

### 4.1.1 SIMD / AVX
У `matmul_O3.s` для функції `matmul_ikj` знайдіть:
```
vbroadcastsd  ...          ; a = A[i][k] копіюється в усі 4 лінії ymm
vfmadd213pd (%rax,%rdx), %ymm3, %ymm1   ; C[j..j+3] += a * B[j..j+3]
```
- `ymm` — 256-бітні регістри AVX = 4 double одночасно;
- `vfmadd…pd` — FMA (fused multiply-add) з розширення FMA3/AVX2: множення і додавання однією інструкцією над 4 числами (**p**acked **d**ouble);
- у `-O0` замість цього скалярні `mulsd`/`addsd` (**s**calar **d**ouble, xmm, 1 число).

`vec_report.txt` (ключ `-fopt-info-vec-optimized`) показує, які цикли компілятор векторизував і якою шириною (`32 byte vectors` = AVX). У `ijk` внутрішній цикл — це редукція `sum += ...` з кроковим доступом до B, тому векторизується погано: без `-ffast-math` компілятор не може переставляти додавання float (зміниться результат округлення). Можна також спробувати `-mavx512f` / `-mprefer-vector-width=512` → `zmm` (8 double).

### 4.2 Порівняння показників
Запустіть `stats.sh` для всіх варіантів і зведіть у таблицю:

```bash
for b in ./matmul_O0 ./matmul_O3; do for v in ijk ikj; do ./scripts/stats.sh $b 1024 $v; done; done
```

| Варіант | Час, с | GFLOP/s | IPC | L1 miss % | LLC miss % | Енергія, Дж |
|---|---|---|---|---|---|---|
| O0 ijk | | | | | | |
| O3 ijk | | | | | | |
| O0 ikj | | | | | | |
| O3 ikj | | | | | | |

Орієнтир (виміряно на Xeon 2.1 ГГц, N=1024): O0 ijk 5.7 с → O3 ijk 4.2 с → O0 ikj 3.1 с → **O3 ikj 0.33 с** (~17× швидше). Зверніть увагу: `-O3` сам по собі мало допомагає наївному коду — вузьке місце пам'ять, а не інструкції. Вирішальна зміна — порядок циклів + векторизація разом.

### 4.3 FlameGraph після
```bash
./scripts/flamegraph.sh ./matmul_O3 1024 ikj
```
Порівняйте з п. 1: частка `matmul_*` зменшується, `init_matrix`/`rand` стають помітно ширшими (бо тепер вони — значна частина загального часу). На `-O3` деякі функції можуть бути вбудовані (inline) і зникнути зі стеку — тому в коді стоїть `__attribute__((noinline))` на функціях множення. Кількість семплів (загальна ширина) теж менша, бо програма працює коротше.

### 4.4 Енергія після
```bash
sudo ./scripts/energy.sh ./matmul_O3 1024 ikj
```
Пояснення: **E = P × t**. Потужність (Вт) у векторизованого коду може бути навіть трохи **вища** (AVX-блоки завантажені, менше простою на очікування пам'яті), але час падає в рази → сумарні джоулі значно менші. Плюс менше звернень до DRAM → менше `energy-ram`. Висновок: швидший код = енергоефективніший код («race to idle»).
